loam how it works

A memory that survives the reboot.

AI coding agents are brilliant and completely amnesiac. Every session starts from zero and re-learns what last session already figured out. loam gives the agent a place to write down what it learns (plain markdown, in your git repo) and a fast way to find it again. This page opens the hood on how the pieces fit: the skills, the runtime, the plugin, the memory, and the search.

The problem it solves

Rediscovery is the tax you pay every session

Picture hiring a genius contractor with total amnesia. Every morning they arrive knowing their craft perfectly, and nothing about your project. The API quirk they diagnosed on Tuesday, the import that only works with one flag, the reason you chose library A over B: they re-derive all of it, from scratch, every single day. You pay for that re-derivation in time and in tokens.

A single AGENTS.md guidance file helps, but it goes stale, grows without bound, and can't hold structured knowledge. What's missing is a substrate: a memory surface an agent can write to in a shape it can later query, that any agent can read, and that you can git log like any other file. That's loam.

The whole bet in one line

Keep the memory as plain markdown in git: no database, no embeddings service, no vendor lock-in. If loam vanished tomorrow, your knowledge is still a folder of notes you can open in any editor. Everything else is machinery for writing those notes well and finding them fast.

The big picture

Four layers, one folder of markdown at the bottom

loam is best understood as sediment. The agent works at the surface; underneath it are layers that each do one job, and at the very bottom sits the memory, the fertile soil the whole thing is named for. Knowledge grows upward: what gets written into the soil resurfaces in the next session's context.

Runtime-agnostic by format

Skills are just SKILL.md files. Any harness that loads skills can run them: no runtime owns the plan or the memory. A plan written under one agent resumes under another.

Installed once, globally

Skills and the binary live under ~/.agents/, not per project. A workspace owns only its own memory. Nothing is added to your PATH.

Degrades gracefully

The search accelerator (qmd) speeds things up when present and is invisible when absent. The substrate is always plain files.

It routes itself

You never memorize skill names. Say "the wiki is wrong about X" or "stopping work" and a router skill dispatches the right one.

01  Layer one

Skills: recipe cards the agent follows

A skill is a single markdown file (SKILL.md) written as a careful procedure: "to add a source to memory, first resolve the file, then read the schema, then check for existing pages, then write, then log it." The agent doesn't invent a process; it follows a tested one. loam ships 21 of them, grouped by job.

Only a skill's one-line description loads at session start; its full body loads only when that skill actually runs. That keeps the agent's context window lean, a running theme in loam's design.

The router is the thing you actually talk to

The loam::using skill isn't a task; it's a dispatcher. It loads at the top of every session and maps plain-language intent onto the right skill, so a person never has to learn the catalogue. It carries the rules that apply across all skills: the memory model, the routing matrix, the admission rubric, and the correction flow.

# you say → the router picks "write a spec for what we discussed" → loam::writing-spec "plan the work from that spec" → loam::planning "stopping work, need to step away" → loam::checkpointing "what does memory say about auth?" → loam::querying-memory "memory is wrong about the retry logic" → loam::amending-memory

The router never does the work itself; it recognizes intent and hands off. That single indirection is why loam feels like one tool instead of twenty-one.

02  Layer two

The plugin & adapter: the doorman

Skills are passive; something has to wake loam up when a session starts and hand the agent its briefing. That's the job of a small marketplace plugin (for Claude Code and Codex) and equivalent adapters (for OpenCode and Cursor). The plugin owns two moments: the SessionStart hook (walk in the door) and the Stop hook (turn just ended).

At startup, the doorman assembles a briefing (the <LOAM_IMPORTANT> block) and injects it straight into the agent's context. That block is the router doc, the exact command to reach the runtime, and a fresh snapshot of this workspace's state.

Why a plugin instead of editing your settings

The plugin owns its hooks through the harness's own plugin system, so loam never permanently scribbles in your settings.json. Install detects which agents you have (Claude Code, Codex, OpenCode, Cursor) and wires each through the same shared Node code, differing only in how that harness expects its hook input and output. One brain, four thin mouths.

The install, in one breath

npx @scchearn/loam setup installs the skills globally, downloads the matching Rust binary from GitHub over HTTPS, verifies its SHA-256 against a published checksum, and smoke-tests it before trusting it: no install script is ever executed. It records everything in one install.json that every hook reads later. update refreshes in place; doctor checks without changing anything; uninstall removes it all.

03  Layer three

The runtime: a fast, honest librarian

Some questions are expensive for an agent to answer by reading files: Is there a wiki here? How stale is it? Which source files changed since I last summarized them? Answering those by hand burns tokens and is fragile across operating systems. So loam ships one tiny Rust binary that answers them in a single line of machine-readable JSON.

It is deliberately boring and trustworthy: read-only, offline, and fail-soft. It inspects files, occasionally asks git a read-only question, prints JSON, and exits. It never edits your code, never phones home, and when a tool is missing it returns "false" rather than crashing.

CommandWhat it answers, in plain terms
state"What's the situation here?" Is there a wiki, is search ready, how many checkpoints, is the tree dirty, and what should I probably do next (the hints).
codegraph"Which source files does memory not yet reflect?" Walk the code, compare against what's recorded, list only what's new or changed.
lint"Is the memory healthy?" Broken links, orphan pages, stale claims, malformed notes, as one finding per line.
datecheck"Are the timestamps consistent?" The one command allowed to rewrite files, and only to fix timezone drift.
checkpoint"Is this restart note valid, and what was I doing?" Verifies a checkpoint's pointers; never blocks a save.
check versions"Do the release version numbers all agree?" An offline pre-commit gate.

The startup probe: state --fast

This is the command the doorman runs every session. The --fast flag skips the two expensive full-tree scans, so it stays cheap enough to run on every start. Its most useful output is the hints array: small, advisory nudges that turn silent state into a suggested next action. Hints are surfaced to you, never auto-run.

# a hint is a nudge, not a command that fires [loam:hint] checkpoint_stale tree dirty, last checkpoint 40 min ago → /loam::checkpointing [loam:hint] code_ingest_pending 3 source files new or changed → /loam::ingesting-codebase [loam:hint] spec_ready_for_plan approved spec has no plan yet → /loam::planning

Other hint kinds cover resumable checkpoints, stale memory (no lint in 7 days), an over-long log, a legacy structure to consolidate, and in-progress plans. Each names a stable key the relevant skill can "satisfy" and suppress once it acts. The loop closes: state signals, a skill acts, the next signal surfaces.

Inside the runtime

The code graph: walk − index = the work list

Re-summarizing an entire codebase every time is wasteful: most files didn't change. loam's code graph solves this the way a good backup tool does: by identity, not by clock. It gives every file a content identity (in a git repo, git's own blob hash) so a file that hasn't changed is recognized as unchanged even if its timestamp moved. Then the answer to "what needs work?" is pure subtraction.

The subtraction has a bonus twist: if a file's blob was already summarized in a sibling git worktree, the diff points the agent at that cached summary instead of paying to write a new one. Work done once is reused everywhere the same bytes appear.

04  The bedrock

Memory: three substrates, one umbrella

"Memory" is the umbrella term for everything loam remembers. Underneath it are three substrates, each with a different lifespan and a different maintainer. Keeping them separate is what stops memory from rotting into a junk drawer.

durable · agent-owned

Wiki

Obsidian-friendly notes under wiki/: topic, entity, concept, and analysis pages, cross-linked with [[wikilinks]]. The lasting knowledge. This is what search indexes.

durable · prompt context

Guidance

AGENTS.md is canonical; CLAUDE.md is a thin shim to it. This is how to work here (commands, conventions, gotchas) loaded as context by the harness.

transient · one restart

Checkpoints

Restart notes under wiki/checkpoints/. Work-state for picking up where you paused, used once, then superseded. Never durable knowledge.

The gate: not everything earns a page

The failure mode of "AI memory" is hoarding: writing down every passing thought until search returns noise. loam guards against that with a three-part admission rubric. A fact earns a durable page only if it clears all three tests. If it doesn't, it's routed elsewhere or discarded.

Agent-owned, self-correcting

The agent writes, corrects, and archives memory without asking permission, humans read it, flag it, and inherit it. When a session reads a page that contradicts fresh evidence, it moves the old page to wiki/.archive/, writes the correction in place, logs it, and keeps going. A human saying "this page is wrong" triggers the exact same flow: a correction, not an approval request.

05  The flywheel

How a piece of work actually moves

The planning skills form a chain from a vague ambition to verified, resumable execution. Each stage produces a real markdown artifact in your repo, and memory feeds every stage. loam even runs this on itself: its own goals/, specs/, and plans/ folders live right in the repo.

06  While you're away

Background workers: memory that tends itself

loam doesn't only remember when you tell it to. When a turn ends, the Stop hook can quietly spin up a detached helper to harvest learnings from the conversation or ingest changed code into memory, using a cheap, fast model, entirely in the background. The design problem is obvious: two background writers editing the same memory at once would corrupt it. loam solves that with a per-workspace lease: a simple lock file that guarantees only one writer touches a workspace's memory at a time.

The harvester only fires when enough new conversation has accumulated since last time; it measures the transcript's growth and skips below a threshold. The ingestor only fires when the code graph reports files pending. Neither ever changes your source, commits, or pushes. On Codex, which can't spawn detached children, the same logic instead instructs Codex to run its own subagent, one brain, adapted per harness again.

The accelerator

qmd: search that speeds up memory, and vanishes when absent

As a wiki grows, grep gets slow and dumb. qmd is an optional local search engine (a separate tool) that indexes the wiki and answers both keyword and meaning-based queries. loam detects it automatically: when it's ready, skills prefer it for finding related pages; when it's not, they fall back to plain grep and glob without missing a beat.

Keyword & semantic

Fast BM25 keyword search for exact terms, plus vector search for "find pages that mean this", used to discover existing related notes before writing a new one, so knowledge links up instead of duplicating.

Discover, then verify

qmd finds candidate paths; the skill still opens the actual file to confirm content. And it covers code too: the wiki/code/ summaries are indexed, so the agent maps the codebase before scanning raw bytes.

A subtle two-step

After writing to a qmd-backed wiki, refreshing the file index (qmd update) is not enough: the vector embeddings go stale until qmd embed runs too. loam treats these as two separate outcomes and never claims a write is "verified" unless both succeed. The kind of honesty that keeps memory trustworthy.

Why it's built this way

The principles under every decision

  • Markdown-first, git-diffable. The memory is files. You can git log it, open it in any editor, and it survives any vendor. No database to migrate, no service to pay for.
  • Harness-neutral. Skills are portable markdown; a plan written under one agent resumes under another. The plan is the asset, not any runtime's private state.
  • Optional tools degrade, never block. qmd speeds up search; the Rust binary speeds up probes. Remove either and loam still works on plain files.
  • Read-only and honest at the edges. The runtime never edits your code or phones home. Startup never downloads or "repairs" silently. Background workers fail closed when uncertain.
  • Small on purpose. Each skill is budgeted in tokens; only descriptions load until a skill runs. Context is treated as the scarce resource it is.
  • Durable is separated from transient. Wiki and guidance last; checkpoints are used once. Conflating them is exactly how memory turns to garbage, so loam refuses to.
What success looks like, in one sentence

Tuesday's session learned something, Wednesday's session reached for it instead of re-deriving it, and a different agent entirely would have found the same thing. That's the whole project. Everything on this page is machinery in service of that one outcome.
